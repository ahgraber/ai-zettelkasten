# Tasks: Chunk Persistence and Contextualization

> Build order within this change: graph-stage foundation (run primitive + schema) → chunk persistence + manifest → contextualization runs → graph work-unit + enqueue (run modes) → stage adapter/UI on the shared runtime.
> The domain groups (foundation, chunk persistence, contextualization) are independent of the shared runtime. The work-unit/enqueue and stage-adapter groups build on the `pipeline-stage-runtime` change (already implemented): contextualization is a worker-driven stage mirroring conversion — a status-bearing work-unit table claimed/leased through the runtime's `StageHandler` / `StageRunner`, with run-status transitions recorded on the run primitive and work-unit lifecycle transitions in `pipeline_events`. Run modes are enqueue patterns over that work-unit table, not separate write paths. The runtime ships no generic operator UI (deferred), so this stage builds its own operator view.
> Tests use a stub LLM client; no live model calls. Run via `uv run pytest tests/graph/`.
>
> **Model revised mid-implementation.** The foundation, chunk-persistence, and contextualization-runs groups were first implemented against an earlier model (run scope = `converted_artifact_id`; all `Chunk` fields on one row; a bare `chunk_run_membership`). The revised model — in design.md and the delta specs — is: runs scoped by the **source `aizk_uuid`**; chunk rows carry **stable identity facts only**, with generation-varying facts (`markdown_hash_xx64`, `splitter_version`, `span`) on the `chunk_run` and its manifest; `chunk_run_membership` becomes **`chunk_run_manifest`** (recording each chunk's `span`); the consumed `conversion_output_id` is recorded on a new **`chunk_run_input`** row; the summary run records its consumed `conversion_output_id`; and each variant records `chunking_run_id` + `summary_run_id` and folds `splitter_version` into its derivation key. Tasks whose built code had to be reconciled to that model were tagged **[rework]** (and were reset to `[ ]` at the time of the revision); genuinely-unaffected tasks kept `[x]`. The **[rework]** tag is retained as provenance — a checked **[rework]** item means that reconciliation is complete and verified.

## Contextualization work-unit + enqueue (run modes)

- [x] Add the graph work-unit table (one row per document / converted artifact), mirroring `conversion_jobs`, plus its Alembic migration in the conversion tree.
  Fields: `id` (local claim handle, never a derivation input), `idempotency_key` (enqueue dedupe so re-enqueueing the same document reuses the open unit rather than creating a second), `conversion_output_id` (local artifact locator, used to fetch the Markdown the unit then splits and persists), `aizk_uuid` (durable source identity), a lifecycle status, attempt count, and retry-scheduling fields.
- [x] Implement the per-document unit-of-work — the full graph write path `split → persist_chunks → summarize → contextualize` (chunk persistence and contextualization are one required pipeline, not separately-gated) — and the two enqueue entry points feeding it through the single worker write path: bulk/backfill (enqueue many, throttled, batched per-document commits) and incremental (enqueue one on ingest); enqueue dedupes on `idempotency_key`.
  The unit-of-work fetches the Markdown via `conversion_output_id`, runs `split` then `persist_chunks` to record (or reuse) the chunking run and chunk rows, then summarizes and contextualizes the just-persisted chunks read in document order (`ordinal`) rather than the `chunk_id`-ordered manifest the chunk store returns.
  It derives every run (chunking/summary/variant) from `aizk_uuid`, `markdown_hash_xx64`, the version stamps, the prompt/model derivation keys, the summary content identity, and the ordered `chunk_id`s — never from `id`, `conversion_output_id`, or any other local row handle.
- [x] Test `tests/graph/test_run_mode.py::test_bulk_and_incremental_same_records` and `::test_incremental_matches_bulk_shape`: the same document in each enqueue mode yields the same run records with identical provenance and derivation-key linkage. **[run-mode independence — bulk / incremental partition]**
